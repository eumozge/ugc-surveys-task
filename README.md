# UGC-опросы

Привет, ревьюер! В задании не хватает части требований, поэтому ниже приведены допущения для реализации в рамках тестового задания. В рабочем проекте я бы сначала обсудил всё с бизнесом, а тут додумываем (:

## Функциональные допущения

- **Выбор ответа.** Примеры содержат взаимоисключающие да/нет, поддерживаем только один вариант ответа.
- **Ответ другое и типы вопросов.** Не поддерживаем. Все варианты автор добавляет
  вручную, если надо на клиенте можно автоматизировать, например добавив шаблоны.
- **Публикация, редактирование и закрытие.** Редактируем только черновик, после
  публикации опрос не меняется. Если надо изменить, создаём новый. Если есть закрытие опроса, можно заменить флаг публикации отдельным полем для состояния (не реализовывал, уверен что понятно как будет выглядеть), потому что опрос простой конечный автомат.
- **Повторное прохождение.** Не поддерживаем.
- **Состояние попытки.** Добавляем поле с состоянием, чтобы не считать статус прохождения опроса
  по ответам при каждом запросе.
- **Пропуск и изменение ответа.** Пропуск не поддерживаем, изменение ответа до завершения опроса да, но кейс редкий, в MVP я бы запретил.
- **Доступ.** Только авторизованный пользователь может пройти опрос.
- **Длительность для статистики.** Считаем как разницу между началом и окончанием прохождения опроса, паузы пользователя учитываем.
- **Вопросы и ответы.** Вопрос относится к одному опросу, варианты ответов неизменяемые после публикации, поэтому хранить текст ответа пользователя на момент ответа отдельно не нужно.
- **Пользовательский контент.** Всё храним как обычный текст, при сохранении санитизируем, а при выводе экранируем.

## Нефункциональные допущения

- **Объём данных.** Числа из ТЗ не нагрузочный профиль: нет DAU/MAU, множителей RPS и так далее. Можно оценить только срез в ~1 млрд записей в самой большой таблице с ответами, но не понятно как быстро достигается это объём, поэтому рассуждения ниже строятся на предположении о постепенном росте сервиса.
- **Кэш.** Если основная реляционная БД перестанет справляться с чтением, можно кэшировать опубликованный опрос вместе с вопросами и вариантами ответов. Допустимо даже с клиента забирать следующий вопрос по ID, а прогресс пользователя достаточно получить только один раз при открытии опроса. После публикации опрос не меняется, поэтому инвалидация не нужна.
- **Аналитика.** Нефункциональных требований по аналитике нет, поэтому сначала метрики считаем на лету и кэшируем. Таблица большая, но непонятно, сколько надо поднимать с диска за раз. Пока потенциальные проблемы вижу для вирусных (популярных, с сотнями тысяч и миллионами попыток) опросов. Далее, если нужно, считаем агрегаты асинхронно или сразу берём аналитическую БД. Даю >90%, что вместо агрегатов надо сразу брать ClickHouse или что-то похожее и не париться.
- **Партиционирование.** Если аналитика в отдельной БД, партиции для основной БД не понадобятся для 1 млрд ответов. Если объёмы кратно больше, то надо думать, может даже другой класс БД сразу взять для ответов пользователей.
- **Индексы.** Внешние ключи индексируются Django, добавил (не везде) пару индексов на уникальность. Уникальность позиции вопросов и ответов на уровне БД не стал добавлять, сортировка стабильная. По остальным индексам всё будет понятно на основе анализа реальных запросов.

## API

- **Текущий вопрос.** `GET /api/v1/surveys/{public_id}/current-question/`

  ```json
  {
    "state": "in_progress",
    "question": {
      "id": 100,
      "text": "Нео, какую таблетку ты выберешь для код-ревью?",
      "choices": [
        {"id": 101, "text": "Синюю: закрыть глаза, нажать approve и верить."},
        {"id": 102, "text": "Красную: открыть коммиты и увидеть, насколько глубока кроличья нора."},
      ]
    }
  }
  ```

- **ViewSet.** Выбрал `GenericViewSet` для опросов, так как можно добавить миксины и закрыть часть функционала из задания.
- **Сервисы.** В задание речь только про view, предполагаю что сервисы в scope задания не входят, поэтому минимум и всё в одном модуле без доп. слоёв.
- **Тесты.** Не писал, как и выше предполагаю что не требовалось.
- **Типизация.** Аннотации Django/DRF не добавлял.
